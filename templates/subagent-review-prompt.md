# 템플릿: 서브에이전트 읽기 전용 검토 프롬프트

## A. 실사용 원문 (`55b37226` 서브에이전트 `ae2ab98d:1`, 경로 가림·발췌)

> [MOEL AI Desk / STEP-01 설계 감사 / 역할: Review]
> 반드시 따를 것: `<repo>/CLAUDE.md`, docs/process/CODING_PRINCIPLES.md(①생각 먼저 ②단순함 ③외과적 변경 ④목표 중심 검증).
> 승인 범위: 읽기 전용 설계 감사. 파일 수정·패키지 설치·유료 API·서버 실행·git 쓰기 금지. `.env` 값과 data/ 실데이터 내용은 출력하지 말 것.
> 불명확하면 추측하지 말고 보고할 것. 실제로 읽은 파일과 줄 번호만 근거로 쓸 것.
>
> ## 배경
> … 작업 트리에 미커밋 문서 변경이 있으며 **현재 작업 트리가 최신 설계**다. 목표: … 최근 결정: D-029, D-030, D-031 … 외부 계정: [개인 계정의 선불 금액·요금제 — 공개본에서 생략]. **설계 작성자의 결론을 옳다고 가정하지 말 것.**
>
> ## 당신의 영역: 결정 기록·Step 계획·운영 규칙·보안·배포·시연
> 읽을 문서: CLAUDE.md, PLAN.md, … docs/DECISIONS.md, docs/STEPS.md, docs/steps/STEP-*.md(전부), docs/SECURITY.md, docs/DEPLOYMENT.md, … .env.example(키 이름만).
>
> ## 확인할 것
> 1. 문서 간 상충, 특히 최신 결정이 반영되지 않은 곳 …
> 2. 과거 결정이 '대체됨'으로 올바르게 표시됐는가, 확정 안 됐는데 확정처럼 쓴 것(모델명·요금·성능·일정).
> 3. 개인정보 처리 vs 서버 보안·비용 보호 충돌 …
> 4. 배포 설계의 빈틈 …
> 5. 각 Step의 선행 조건·작업·테스트·완료 기준·승인 항목이 명확한가 …
> 6. 운영 규칙이 서로 모순되지 않는가 …
> 7. 시연 요구가 Step 완료 기준에 연결돼 있는가. 불필요하게 복잡한 프로세스·설계.
>
> ## 보고 형식 (한국어, 2,000단어 이내)
> 발견마다 한 줄 표: `ID | 분류(A 사용자 결정 필요 / B 합리적 기본값 가능 / C 표현·중복) | 심각도(높음/중간/낮음) | 근거 파일:줄 (2곳 이상이면 모두) | 문제 | 제안`. 확인했지만 문제없던 주요 항목도 마지막에 3~5줄로 요약. 추측은 '추측'이라고 표시.

같은 구조로 3개 영역(결정·Step·운영 / RAG·법령·데이터·평가 / API·상태·화면)을 병렬로 맡겼고, 지적 89건이 A 15 / B 약 45 / C 약 15로 분류되었습니다 [보고서: `55b37226:639`].
