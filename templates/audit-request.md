# 템플릿: 독립 감사 요청서

## A. 실사용 원문

### A-1. Codex 감사 요청서 전문 (`codex1:25`, 사용자가 `codex_only_requests.md`로 제공. 초안은 ChatGPT가 작성, `gpt:6af696c2/011c2cdc`, [05-chatgpt.md](../case-studies/moel-ai/05-chatgpt.md))

> # MOEL AI Desk — 독립 기술 설계 감사
>
> 현재 이 프로젝트는 Claude Code를 이용해 개발 중이며, STEP-01 상세 설계가 거의 완료된 상태입니다.
>
> 당신은 개발자가 아닌 **독립 기술 설계 감사자(Independent Architecture Reviewer)** 역할을 맡습니다.
>
> 목표는 기존 설계를 재작성하는 것이 아니라, 구현 전에 발견할 수 있는 중대한 구조적 오류와 설계 불일치를 찾는 것입니다.
>
> ## 작업 지침
> 1. 프로젝트 저장소 전체 구조를 탐색하세요.
> 2. CLAUDE.md, DECISIONS.md 등 실제 존재하는 핵심 규칙·의사결정 문서를 확인하세요.
> 3. 최신 ERD, API, SSE, 상태 전이, 시퀀스 다이어그램, RAG, 보안, 테스트 계획을 찾아 읽으세요.
> 4. 설계 문서끼리 비교하고 현재 코드 및 테스트와 교차 검증하세요.
> 5. 설계에만 존재하고 아직 구현되지 않은 기능은 정상적인 미구현 상태와 실제 불일치로 구분하세요.
> 6. 확인된 문제에는 파일 경로와 가능한 경우 줄 번호를 표시하세요.
> 7. 발견한 문제를 P0(구현 전 해결), P1(중요), P2(개선 사항)로 분류하세요.
> 8. 각 문제의 발생 조건, 실제 영향, 최소 수정 방안, 검증 방법을 제시하세요.
>
> ## 중점 감사 대상
> SQLite ERD 및 데이터 무결성 / 단건·100건 일괄 처리 상태 전이 / 멱등성·동시성·재시도 / SSE 이벤트 순서와 재연결 / API·프론트엔드 계약 / ChromaDB 3종 검색과 LangGraph / 법령·근거·인용 검증 / 개인정보·접근 키·데이터 보존 / 예산 예약·정산 / Railway·Vercel 배포 구조 / 테스트의 누락과 경계 조건
>
> ## 중요한 제약
> - 모든 작업은 읽기 전용으로 수행합니다.
> - 코드·문서·설정 파일을 수정하지 마세요.
> - 테스트 실행으로 파일이 생성되거나 변경될 수 있다면 먼저 승인받으세요.
> - 커밋·푸시·배포·유료 API 호출을 하지 마세요.
> - 기존 설계를 최대한 유지하는 최소 변경 해결책을 우선하세요.
> - 확실하지 않은 위험은 검증된 결함과 구분하세요.
>
> 우선 저장소 구조를 파악하고 감사 계획 및 검토 대상 파일 목록을 보고하세요. 이후 제 승인을 받아 영역별 감사를 진행합니다.
>
> ### 추가 프로젝트 상황
> 현재 STEP-01 상세 설계는 작성되었으나 최종 사용자 승인 전입니다. Claude Code가 작성한 최신 설계 문서 중 일부는 아직 커밋되지 않았으며, UI/UX의 A+ 시안과 랜딩 페이지 설계도 최종 문서 반영 전입니다.
> - Git에 커밋된 파일뿐 아니라 현재 작업 디렉터리의 미커밋 설계 문서도 확인합니다.
> - 미커밋 변경 사항을 수정하거나 되돌리지 않습니다.
> - 최신 설계 문서와 과거 문서를 구분합니다.
> - 아직 구현되지 않은 설계는 코드 오류로 판단하지 않습니다.
> - UI/UX의 최종 디자인은 미확정으로 간주합니다.
> - 현재 설계에서 발견한 위험과 향후 구현 시 발생할 수 있는 위험을 구분합니다.
> - 다른 개발 에이전트가 작업 중이므로 읽기 전용을 유지합니다.
>
> 우선 프로젝트 구조와 검토 대상 파일 목록만 보고하고, 실제 영역별 감사는 제 승인 후 시작해 주세요.

참고: 요청서의 "LangGraph"는 감사 대상 목록에 남아 있었지만, 사용자는 LangGraph를 필수 구성에서 제외했습니다(`fc1439ba:57`).

### B-2. 감사 요청서

```markdown
# {프로젝트} — 독립 설계 감사 ({N}차)

## 역할과 목표
당신은 개발자가 아닌 **독립 설계 감사자**입니다. 설계를 다시 쓰는 것이 아니라,
구현 전에 찾을 수 있는 구조적 오류와 문서 간 불일치를 찾는 것이 목표입니다.
설계 작성자의 결론을 옳다고 가정하지 마세요.

## 현재 상황
- 단계: {예: STEP-01 설계 작성 완료, 사용자 최종 승인 전}
- 기준: Git 커밋 `{hash}` + 작업 트리의 미커밋 문서(최신)
- 이미 구현된 코드: {있음/없음, 범위}  ← 설계 이전 코드가 있으면 반드시 적기
- 확정되지 않은 것: {예: 최종 시각 디자인}

## 지침
1. 핵심 규칙·결정 문서({파일})를 먼저 읽으세요.
2. 계약 문서({ERD, API, 이벤트, 상태 전이, 시퀀스, 보안, 테스트 계획})를 서로 비교하고 코드·테스트와 교차 검증하세요.
3. **정상적인 미구현**과 **실제 불일치**를 구분하세요.
4. **검증된 결함**과 **불확실한 위험**을 구분하세요.
5. 문제마다: ID | P0(구현 전 해결)/P1(중요)/P2(개선) | 근거 파일:줄 | 발생 조건 | 영향 | 최소 수정안 | 검증 방법

## 중점 대상
- {영역 1} / {영역 2} / …

## 제약
- 읽기 전용. 코드·문서·설정 수정 금지. 쓰기는 `{응답 파일}`만.
- 파일을 만들거나 바꿀 수 있는 테스트 실행은 먼저 승인.
- 커밋·push·배포·유료 API 호출 금지.
- 미커밋 변경을 수정하거나 되돌리지 않음.
- 최소 변경 해결책 우선.

## 진행 순서
먼저 **감사 계획과 검토 대상 파일 목록만** 보고하세요. 영역별 감사는 제 승인 후 시작합니다.
결과는 `{응답 파일}`에 덮어쓰고 다시 읽어 저장을 확인하세요.
```
