# 00. 설계 단계 전체 흐름

## 한 줄 요약

**범위 합의 → 실측 → 결정 기록 → 설계 → 사용자 승인 → 독립 감사 → 수정·재대조 → 최종 검증 → 기준 태그 → 구현 시작 승인**

이 순서는 MOEL AI 설계 과정에서 실제로 일어난 흐름을 정리한 것입니다 [사실]. 다만 실제로는 깔끔하게 직선으로 진행되지 않았고, 1단계 도중 코드가 먼저 만들어졌다가 중단되었습니다([01단계](01-requirements-and-scope.md) 참고).

## 역할 분담

| 역할 | 실제로 한 일 [사실] | 권장 [권장] |
|---|---|---|
| **사용자** | 목적·범위 재정의, 외부 확인(지도교수·데이터 제공처), 질문 묶음에 답변, Step·감사 차수 승인, **AI 사이의 모든 중계**(복사·붙여넣기, 요청·응답 파일), 감사 요청서 파일 생성(초안 작성은 ChatGPT, [05](../case-studies/moel-ai/05-chatgpt.md)) | 최종 결정권자. "무엇을 하지 않을지"를 명확히 말하는 역할. 충돌하는 지시를 보내지 않도록 이전 지시를 함께 적는 역할 |

## AI끼리는 연결되어 있지 않다 [사실]

MOEL AI에서 ChatGPT·Claude Code·Codex는 **서로 자동으로 연동되지 않았습니다.** 사용자가 Claude Code의 보고를 ChatGPT에 붙여넣고, ChatGPT가 쓴 지시문을 `message.md` 파일이나 붙여넣기로 Claude Code에 전달했으며, Codex에는 감사 요청서 파일을 만들어 "파일을 읽어줘"만 입력했습니다. 이 구조의 장점은 사용자가 모든 지시를 보고 막을 수 있다는 점이고, 위험은 **서로 모순되는 지시가 같은 AI에 도착해도 아무도 충돌을 걸러 주지 않는다**는 점입니다(11-12 중단 지시와 개발 진행 지시, [05-chatgpt.md E-1](../case-studies/moel-ai/05-chatgpt.md)). 중계 검토 양식은 [templates/cross-review-prompt.md](../templates/cross-review-prompt.md).

## 모든 단계에 적용되는 공통 원칙 [권장]

1. **실행 전 범위 확인.** 기능 목록이 담긴 지시도 "지금 만들라"는 말이 명확하지 않으면 계획의 입력으로 다룬다.
2. **추측 금지, 실측 우선.** 수치·구조·외부 조건은 파일·문서·공식 자료로 확인하고, 확인 못 하면 "미확인"이라고 쓴다.
3. **지우지 말고 대체.** 바뀐 결정은 "대체됨 → 새 ID"로 남긴다.
4. **보류는 좁게.** 외부 답변을 기다리는 항목만 보류하고 나머지는 진행한다.
5. **목적이 범위를 정한다.** "상용이 아니라 발표용"처럼 목적을 다시 말하는 것만으로 과설계를 줄일 수 있다. MOEL AI에서 AI는 여러 번 과설계 쪽으로 출발했고, 사용자가 같은 표현으로 범위를 반복해 줄였다(`d39ff7ed:496`, `55b37226:322`, `fc1439ba:193`).
6. **통과의 층을 구분.** "문서에 반영됨", "코드 구현됨", "테스트 통과", "사용자 확인"은 서로 다른 상태다.
7. **증거로 보고.** "통과했다"는 말에는 실제 실행 출력이 따라와야 한다.
8. **위험한 행동은 각각 승인.** 유료 API 호출, 외부 배포, push, 태그, 이력 변경은 하나씩 따로 승인받는다.
9. **충돌하는 지시는 실행 전에 확인.** 새 지시가 이전의 중단·보류 지시와 어긋나면 어느 쪽인지 되묻는다(11-12 사례).
10. **수치는 처리 단계와 함께.** 원시 / 정제 / 최종 사용 행 수를 구분해 적는다(13,597 → 11,380 사례, [05-chatgpt.md E-2](../case-studies/moel-ai/05-chatgpt.md)).

## 이 문서들의 읽는 법

각 단계 문서는 같은 틀을 씁니다: **목적 → 절차 → 완료 기준 → 흔한 실패와 복구 → MOEL AI 근거 → MOEL 전용 설정**. 근거와 MOEL 전용 설정은 참고용이고, 다른 프로젝트에 적용할 것은 "절차"와 "완료 기준"입니다.
