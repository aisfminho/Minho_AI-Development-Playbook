# 08. 구현 전 최종 검증

## 목적

설계를 닫기 전에 **남은 질문을 모두 꺼내고**, 현재 저장소 상태를 실제 실행 결과로 확인합니다. 이 단계에서는 고치지 않고 확인만 합니다.

## 절차 [권장]

### 1) 미결 질문 도출

1. AI에게 "모든 파일을 확인하고, 구현 전에 확정 짓고 싶은 것을 전부 물어봐 달라"고 요청합니다.
2. AI는 영역을 나눠(예: 과정·일정 / 데이터·RAG / UI·배포) 읽기 전용 서브에이전트에 맡기고, 메인도 한 영역을 직접 봅니다.
3. 서브에이전트가 낸 수치는 메인이 **집계로 다시 재서** 확인합니다.
4. 질문은 추천안과 함께 묶어 제시하고, 사용자 답변을 결정으로 기록합니다.

### 2) 검증만 하는 점검 (고치지 않음)

| 점검 | 방법 |
|---|---|
| 테스트 | 백엔드·프론트 테스트 전체 실행. **실패하면 원인만 분석, 코드는 수정하지 않음** |
| 변경 파일 | 수정·삭제·신규 파일 목록, 스테이징 상태 |
| 민감정보 | 커밋 대상에서 전화번호·주민번호·이메일·API 키·개인 키·사용자 절대 경로 검색 |
| 문서 링크 | 깨진 링크, 옛 문구 |
| 브랜치 | 현재 브랜치, 원격과의 차이(언제 fetch했는지 함께 적기) |

### 3) 보고

- 결과는 **실제 실행 출력**(통과 수, 실패 수)으로 보고합니다.
- 테스트가 **어떤 코드의 결과인지** 적습니다(설계 단계 이전에 만든 코드인지 등).
- 남은 결함과 차단 조건을 다시 적습니다.
- 다음 승인 사항을 하나씩 나열합니다(commit → push → tag 각각).

## 완료 기준

- [ ] 미결 질문이 모두 결정되었거나, "관련 Step 시작 전 결정"으로 명시되었다
- [ ] 테스트 실행 결과가 실제 출력으로 보고되었다
- [ ] 커밋 대상 파일 목록과 민감정보 검사 결과가 있다
- [ ] 남은 코드 결함과 차단 조건이 기록되어 있다

## 흔한 실패와 복구

| 실패 | 복구 |
|---|---|
| "테스트 통과"가 설계 완료처럼 읽힘 | 그 테스트가 어떤 코드의 것인지, 설계 감사 판정과 무엇이 다른지 함께 적음 |
| 검증 중에 고치기 시작함 | 검증과 수정을 분리. 수정은 별도 승인 |
| 미결 질문이 너무 많음 | 지금 정할 것과 "관련 Step 시작 전에 정할 것"을 나눔 |
