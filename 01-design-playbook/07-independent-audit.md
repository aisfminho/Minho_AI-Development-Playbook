# 07. 독립 감사

## 목적

설계 작성자(메인 에이전트)가 스스로 못 보는 결함을, **다른 맥락·다른 도구의 감사자**가 구현 전에 찾게 합니다.

## 두 종류의 독립 검토 [권장]

| 종류 | 감사자 | 쓰임 |
|---|---|---|
| 내부 검토 | 같은 도구의 서브에이전트(읽기 전용) | 영역 분할 감사, 정합성 재검증, 감사 반영 대조 |
| 외부 감사 | 다른 도구(예: Codex)의 별도 세션 | 전체 설계의 독립 감사, 반영 결과 재검증 |

## 절차 [권장]

1. **채널을 분리합니다.** 감사자 전용 요청·응답 파일을 두고, 개발 에이전트는 그 파일을 읽지 않습니다. 사용자가 결과를 전달합니다.
2. **권한부터 시험합니다.** 감사자에게 "응답 파일 끝에 한 문장만 추가 → 다시 읽어 확인 → 실패하면 우회하지 말고 오류 보고"를 시킵니다.
3. **감사 요청서를 보냅니다**([templates/audit-request.md](../templates/audit-request.md)). 요청서는 설계 작성자(Claude Code)와 **다른 도구**가 초안을 쓸 수도 있습니다. MOEL AI에서는 ChatGPT가 초안을 쓰고 사용자가 파일로 만들었습니다. 이 경우 요청서를 **사용자가 한 번 읽고** 감사 범위가 설계 작성자 쪽 가정에 치우치지 않았는지 확인합니다.
   - 역할: 개발자가 아닌 독립 감사자. 목표: 재작성이 아니라 결함 찾기
   - 범위: 커밋되지 않은 최신 문서도 포함하되 수정·되돌리기 금지
   - 구분: 정상적인 미구현과 실제 불일치, 검증된 결함과 불확실한 위험
   - 분류: P0(구현 전 해결) / P1(중요) / P2(개선), 문제마다 발생 조건·영향·최소 수정안·검증 방법
   - 순서: **감사 계획과 대상 파일 목록 먼저 보고 → 사용자 승인 → 영역별 감사**
4. **차수마다 승인합니다.** 1차 → 2차 → 3차(최종)를 사용자가 각각 승인합니다.
5. **메인 에이전트가 지적을 원본과 대조해 반영합니다.** 감사가 든 문서·코드 줄을 직접 열어 확인하고 판정을 적습니다(`확인` / `확인(코드)` = 코드에서 결함 경로 직접 확인).
6. **상태표로 관리합니다**([templates/audit-status-table.md](../templates/audit-status-table.md)). 상태 용어를 정의하고, 차단 조건(언제까지 고쳐야 하는가)을 적습니다.
7. **재검증합니다.** 감사자가 반영 결과를 다시 대조합니다. PARTIAL은 보완 후 **독립 재대조 전까지 PASS로 표시하지 않습니다.**
8. **판정을 두 층으로 보고합니다.**
   - 설계 반영 판정: PASS / PARTIAL / FAIL
   - 구현 상태: 대기 / 구현됨 / 테스트 통과 / 해당 없음
   - "설계 PASS"를 "구현 완료"로 말하지 않습니다.
9. **감사자가 확인하지 못한 범위를 기록합니다.** 원목록이 없거나 끝까지 읽지 못한 문서는 "미확인 범위"로 남깁니다.
10. **이력은 고쳐 쓰지 않습니다.** 앞선 "모두 반영" 기록이 틀렸으면 새 이력 줄로 바로잡습니다.

## 완료 기준

- [ ] 모든 감사 항목에 설계 판정과 구현 상태가 따로 있다
- [ ] PARTIAL 항목이 재대조를 거쳐 PASS가 되었거나, 미해결로 명시되었다
- [ ] 코드 결함으로 확인된 항목은 고칠 Step과 차단 조건이 있다
- [ ] 미확인 범위가 기록되어 있다

## 흔한 실패와 복구

| 실패 | 복구 |
|---|---|
| 감사자에게 쓰기 권한이 없어 수정 불가 | 우회하지 않고 수정안만 응답 파일에 작성 → 사용자가 전달 → 메인이 대조 후 반영 |
| 감사 원문이 보관되지 않음 | 감사 원문을 별도 파일로 보존(Git 제외 가능)하고 상태표에 경로를 적음 |
| 반영 문서의 일부만 리뷰됨 | 상태표 이력에 "미확인 범위"를 적고 다음 차수에서 대상으로 지정 |
